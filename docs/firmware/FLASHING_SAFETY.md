# Flashing safety

## Classification rule

An image is **VERIFIED FOR FLASHING** only when all mandatory compatibility and
package checks pass, the installation mechanism is understood, and sufficient
evidence supports use on the exact target device. A single failed or unknown
mandatory check prevents that classification. A successful build, a correct
filename and a valid checksum are each necessary but insufficient.

No image in this worktree is approved for flashing. **Do not flash any image
generated by this project on the basis of a successful build or a passing
structural check.**

## What was actually verified

`tools/validate_upt.py` independently opens the `.upt` as an ISO 9660 image,
reads `ota_update.in`, checks the number and ordering of the 512 KiB chunks,
verifies the MD5 chain (each filename suffix equals the previous chunk's MD5),
compares the per-chunk manifest, reassembles each component and checks it
against the MD5 **declared inside the same image** (not a vendor reference), then
reads `device-name` from the rootfs. This proves internal consistency only: a
consistently rebuilt or mislabelled image would also pass. It was executed against
`r1.upt` (structural pass, `HiBy R1`) and against deliberately wrong-device,
truncated and corrupted inputs (all rejected). Raw JSON reports are in
`docs/QA/validation/`.

The validator deliberately does **not** claim to verify:

* that the device will accept the image;
* that the bootloader or recovery enforces device identity;
* that the embedded kernel matches the hardware;
* that a signature is absent because none is required;
* that the embedded kernel is the right architecture/model (only its MD5 is
  checked) or that the grown rootfs fits the device's MTD partition;
* that a failed update can be recovered;
* that any DAC, display, touch or button path works.

## Format and signature findings

The `.upt` is an ISO 9660 image containing OTA metadata and MD5-chained split
components. No signing tool, signature block or public-key verification was
found in either packer, in the OTA client, or in the release workflow. Integrity
rests on the MD5 chain and the SHA-256 digests published with GitHub release
assets. Source comments state that the recovery kernel does not check what it is
given. This makes the `device-name` check in the packer and the validator the
only practical cross-device guard, and it is a software-side guard only.

## Required evidence before reclassification

For each device, all of the following would be needed before a CONDITIONALLY
VERIFIED classification could be considered, and still more before VERIFIED:

1. an official vendor firmware package with a published checksum, compared
   structurally with the generated image;
2. documentation or tool evidence for the exact installation procedure,
   filename, location and version preconditions;
3. clarity on signature requirements and legitimate access to signing if
   required;
4. independent confirmation that the recovery path survives a failed update;
5. for V1, a merged V1 codebase and an independently built, validated image;
6. explicit user authorisation before any physical test.

## Safety principle

Device safety takes priority over delivery. If evidence is insufficient, the
image stays NOT VERIFIED. No check in this document has been downgraded to pass
a gate.
